# ESE Pre-Processor Language Guide

`esepp` is a small preprocessor for one job: allow programmers to write ESE-style
state machines in C++23. 

The ESE Pre-Processor (ESEPP) does not port over the full ESE syntax, instead 
it acts as a kind of template programming with custom syntax. 
The ESEPP does not parse C++, have type/effect awareness, or have symbol resolving.
It only understands the state-machine syntax documented here.

## The Pipeline

1. Write normal C++ declarations first: variables, queues, functions, hardware
   wrappers, or any helpers your generated state machine will call.
2. Add an ESE block in a C++ block comment.
3. Run `esepp` on the project folder.
4. Build with your normal C++23 compiler.
5. Debug the generated C++ like ordinary C++.

```powershell
esepp .
clang++ -std=c++23 src\main.cpp -o app.exe
```

If `esepp` is not on `PATH`, run the executable directly:

```powershell
C:\path\to\esepp.exe .
```

## File Scanning

`esepp [root]` scans recursively from `root`. If `root` is omitted, it scans
the current directory.

Supported source extensions:

- `.cpp`
- `.hpp`
- `.h`
- `.cc`
- `.cxx`
- `.hxx`

Ignored folders:

- `.git`
- `build`
- `cmake-build-debug`
- `cmake-build-release`
- `.vs`
- `.idea`

The tool modifies files in place. It keeps the ESE block and refreshes the
generated C++ section below it.

## ESE Block Format

Every state machine must live inside this marker pair:

```cpp
/* #ESE-BEGIN

machine Example {
    initial Idle;

    state Idle {
        on started -> Running;
    }

    state Running {
        on stopped -> Idle;
    }
}

conditionals Example {
    started = startButtonPressed();
    stopped = stopButtonPressed();
}

actions Example {
    enter Running {
        startMotor();
    }

    exit Running {
        stopMotor();
    }
}

#ESE-END */
```

After running `esepp`, the file will contain:

```cpp
// #ESE-GENERATED-BEGIN: Example
// Generated by esepp. Do not edit this section by hand.

class Example
{
    // generated C++
};

// #ESE-GENERATED-END: Example
```

It is not recommended to edit the generated code by hand. 
Rather it's encouraged you change the ESE block or the C++
helpers, then run `esepp` again.

## Machine Syntax

One ESE block supports exactly one `machine`.

```ese
machine <MachineName> {
    initial <StateName>;

    state <StateName> {
        on <ConditionName> -> <TargetState>;
    }
}
```

Rules:

- `MachineName`, state names, and condition names are identifiers.
- One `initial` state is required.
- The initial state must be declared as a `state`.
- A machine needs at least one state.
- Duplicate state names are errors.
- Transition targets must name declared states.
- Transitions are checked top to bottom inside the current state.
- The first true transition wins.

Example:

```ese
machine Door {
    initial Closed;

    state Closed {
        on openRequested -> Open;
    }

    state Open {
        on closeRequested -> Closed;
    }
}
```

## Conditionals

The `conditionals` block maps transition names to raw C++ expressions.

```ese
conditionals Door {
    openRequested = buttonPressed && !locked;
    closeRequested = closeSwitchActive();
}
```

Rules:

- The block name must match the machine name.
- Every transition condition must have one matching conditional.
- Duplicate conditional names are errors.
- The expression is copied into generated C++ as `return <expression>;`.
- The expression must end with `;`.
- `esepp` does not type-check or rewrite the expression.

Generated shape:

```cpp
bool conditionOpenRequested()
{
    return buttonPressed && !locked;
}
```

Keep conditionals side-effect-light when you can, the ESEPP is not effect-aware. 
As such, it will not catch errors made when generating equivalent C++ code.
Actions are usually a better place for state changes.

## Actions

The `actions` block defines optional `enter` and `exit` bodies for states.

```ese
actions Door {
    enter Open {
        unlockLatch();
        turnOnLight();
    }

    exit Open {
        turnOffLight();
    }
}
```

Rules:

- The block name must match the machine name.
- `enter <StateName>` runs after transitioning into that state.
- `exit <StateName>` runs before leaving that state.
- Actions are optional.
- Missing actions generate empty functions.
- Every action state must be a declared state.
- Duplicate `enter` or duplicate `exit` actions for one state are errors.
- Action bodies are copied as raw C++ statements.

The constructor enters the initial state at once:

```cpp
Door door; // calls enterClosed()
```

## Generated C++ API

For a machine named `Door`, `esepp` generates a C++ class named `Door`.

Public API:

```cpp
Door door;
door.update();
Door::State state = door.getState();
```

Generated members:

- `enum class State` with one value per ESE state.
- Constructor that calls the initial state's `enter` function.
- `void update()` dispatches based on the current state.
- `State getState() const` returns the current state.

Generated private helpers:

- `update<State>()` checks transitions for one state.
- `condition<Condition>()` returns the raw C++ conditional expression.
- `transitionTo(State nextState)` runs exit, changes state, then runs enter.
- `enter<State>()` and `exit<State>()` contain action bodies or empty bodies.

## Writing C++ Around The Machine

Place C++ helpers before the ESE block when generated code needs them:

```cpp
bool buttonPressed = false;
bool motorRunning = false;

bool shouldStart()
{
    return buttonPressed;
}

void startMotor()
{
    motorRunning = true;
}

/* #ESE-BEGIN

machine Motor {
    initial Stopped;

    state Stopped {
        on startRequested -> Running;
    }
}

conditionals Motor {
    startRequested = shouldStart();
}

actions Motor {
    enter Running {
        startMotor();
    }
}

#ESE-END */
```

Then use the generated class from ordinary C++:

```cpp
int main()
{
    Motor motor;

    buttonPressed = true;
    motor.update();

    return motor.getState() == Motor::State::Running ? 0 : 1;
}
```

## Example: Three-Floor Elevator

This example models a small elevator where physical button requests are served
before remote requests, then car commands are accepted after arrival.

```ese
machine ElevatorController {
    initial Idle;

    state Idle {
        on physicalRequestPending -> DispatchPhysical;
        on remoteRequestPending -> DispatchRemote;
    }

    state DispatchPhysical {
        on targetIsCurrentFloor -> Arrived;
        on targetAboveCurrentFloor -> MovingUp;
        on targetBelowCurrentFloor -> MovingDown;
    }

    state DispatchRemote {
        on targetIsCurrentFloor -> Arrived;
        on targetAboveCurrentFloor -> MovingUp;
        on targetBelowCurrentFloor -> MovingDown;
    }

    state Arrived {
        on carCommandReceived -> DispatchCarCommand;
        on arrivalWaitExpired -> Idle;
    }

    state DispatchCarCommand {
        on targetIsCurrentFloor -> Arrived;
        on targetAboveCurrentFloor -> MovingUp;
        on targetBelowCurrentFloor -> MovingDown;
    }

    state MovingUp {
        on reachedTargetFloor -> Arrived;
    }

    state MovingDown {
        on reachedTargetFloor -> Arrived;
    }
}

conditionals ElevatorController {
    physicalRequestPending = hasPhysicalRequest();
    remoteRequestPending = hasRemoteRequest();
    carCommandReceived = hasCarCommand();
    arrivalWaitExpired = secondsSinceArrival >= 10;
    targetIsCurrentFloor = targetFloor == currentFloor;
    targetAboveCurrentFloor = targetFloor > currentFloor;
    targetBelowCurrentFloor = targetFloor < currentFloor;
    reachedTargetFloor = currentFloor == targetFloor;
}

actions ElevatorController {
    enter DispatchPhysical {
        acceptNextPhysicalRequest();
    }

    enter DispatchRemote {
        acceptNextRemoteRequest();
    }

    enter DispatchCarCommand {
        acceptNextCarCommand();
    }

    enter MovingUp {
        closeDoors();
        commandMotorUp();
    }

    enter MovingDown {
        closeDoors();
        commandMotorDown();
    }

    exit MovingUp {
        stopMotor();
    }

    exit MovingDown {
        stopMotor();
    }

    enter Arrived {
        stopMotor();
        openDoors();
        startArrivalWait();
    }

    exit Arrived {
        closeDoors();
    }
}
```

The priority behaviour comes from transition order in `Idle`: physical requests
are checked before remote requests.

The 10-second timeout is a normal C++ state exposed
through a conditional:

```ese
arrivalWaitExpired = secondsSinceArrival >= 10;
```

See `examples/elevator.cpp` for a complete compilable version.

## Debugging Generated Code

Generated code is meant to be readable. You can debug it directly.

Useful places to set breakpoints:

- `update()` to see which state is active.
- `update<State>()` to watch transition checks in order.
- `condition<Condition>()` to inspect raw condition values.
- `transitionTo(...)` to watch exit/enter order.
- `enter<State>()` and `exit<State>()` to debug action bodies.

Recommended workflow:

1. Read/Debug the ESE block first.
2. Run `esepp`.
3. Open the generated section below the block.
4. Build normally.
5. Set breakpoints in generated functions or in your C++ helper functions.
6. If behavior is wrong, edit the ESE block or helper C++, then regenerate.

Because the original ESE block is preserved, generated code and human-readable
state-machine intent live together in the same source file.

## Diagnostics

On structural errors, `esepp` prints an error and exits non-zero.

Example:

```text
esepp error: src/main.cpp
Machine Door: transition target 'Openn' does not match any declared state.
Known states: Closed, Open
```

Common validation errors:

- Missing machine block.
- More than one machine in one ESE block.
- Missing initial state.
- Initial state not declared.
- Duplicate state.
- Transition target not declared.
- Transition condition missing from `conditionals`.
- Duplicate conditional.
- Action refers to an unknown state.
- `conditionals` or `actions` block names do not match the machine name.

## Regeneration

Running `esepp` repeatedly is expected.

If a generated section already exists immediately below an ESE block, `esepp`
replaces that section. It does not append a second generated copy.

```text
files scanned: 1
ESE blocks found: 1
generated sections updated: 0
```

An update count of `0` means the generated code already matched the ESE block.

## Supported Syntax Summary

```ese
machine <MachineName> {
    initial <StateName>;

    state <StateName> {
        on <ConditionName> -> <TargetState>;
    }
}

conditionals <MachineName> {
    <ConditionName> = <raw C++ expression>;
}

actions <MachineName> {
    enter <StateName> {
        <raw C++ statements>
    }

    exit <StateName> {
        <raw C++ statements>
    }
}
```

## Limitations

`esepp` does not support:

- Multiple machines in one ESE block.
- Nested states.
- Timers as ESE syntax.
- Guards beyond named conditionals.
- Event payloads.
- Diagrams.
- Generated headers.
- C++ parsing.
- Type checking.
- Name resolution.
- Imports or modules.
- Any full-language ESE features.

Use C++ for data structures, queues, timers, hardware access, logging, and
main logic. Use ESE syntax only to describe the state-machine shape.
